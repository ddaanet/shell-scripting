# Plan: bash 3.2 lint in the PostToolBatch hook

Implements `plans/2026-10-31-bash32-lint-family-brief.md`. Decided by my human
partner (2026-11-01, defaults accepted): the lint runs inside the hook, pattern 3
flags every unguarded `printf -v … %b`, and the pass runs even without
shellcheck.

## Shape

- New script `hooks/scripts/bash32-lint.sh` (POSIX `sh`, BSD-safe, the
  self-application rule): takes shell file paths as arguments, prints one finding
  per line in shellcheck's gcc shape,
  `file:line:col: warning: <message> [bash32-N]`, exits 0 whether or not it
  found anything. It never decides whether a file is shell — the hook already
  has. The hook locates it as `$(dirname "$0")/bash32-lint.sh`, since the hook
  command already passes the script by its `${CLAUDE_PLUGIN_ROOT}` path. The
  `just precommit` shellcheck line gains the new script. (A split from the
  accepted "extra pass inside the hook": it buys a script the tests can call
  directly. Open question 1.)
- `shellcheck-on-edit.sh` runs it on the same positional list, concatenates its
  output with shellcheck's, and reports the combined count. Only the user's
  summary wording changes: `shell lint: N findings`. The single-JSON-object exit
  contract, the D3 channel split and `suppressOutput` stay.
- Missing shellcheck: the one-time notice stays; the bash 3.2 pass still runs,
  and its findings are reported. This restructures the hook rather than adding
  to it: the notice branch's early `exit 0` goes, the notice and the findings
  share one `systemMessage` and one JSON object, and the whole script is
  re-audited (self-application rule). Missing `jq` stays silently inert (D5).

## Patterns (contracts)

Each is a line-level match over the file under `LC_ALL=C`; a single-quoted
string or a comment that happens to match is a tolerated false positive (the fix
is still harmless). Every finding names its fix, and every pattern has a
semantics-preserving rewrite the lint accepts, so no suppression comment is
added.

1. `$name` (unbraced, `[A-Za-z_][A-Za-z0-9_]*`) immediately followed by a byte
   ≥ 0x80. The match spells byte ranges explicitly under `LC_ALL=C`, never a
   ctype class (`[:print:]`, `[:alnum:]`): macOS libc classifies 0x80-0xFF as
   printable in UTF-8, so a class-based match differs on the Mac where no Linux
   test sees it. Any `awk` runs as `LC_ALL=C awk`. Fix: `${name}`. Not flagged: `${name}…`, `$1…`, `$name` followed by
   ASCII.
2. `LC_ALL`, `LANG` or `LC_CTYPE` assigned as a command prefix (optionally among
   other prefix assignments) in front of a bash builtin. The builtin set is
   bash 5's `enable -a`, frozen into the script: a superset of 3.2's, and the
   extras are harmless (a prefix before `mapfile` cannot run under 3.2 anyway).
   The brief's "don't freeze a list" concern applies to a list of
   *locale-sensitive* builtins, which this is not. Fix:
   `$(LC_ALL=C; cmd …)` or save/assign/restore; the message mentions that the
   subshell form can draw SC2030. Not flagged: the prefix before an external
   command (`LC_ALL=C sed`), a standalone assignment (`LC_ALL=C; printf`),
   `export LC_ALL=C`.
3. `printf -v <var> <fmt>` where `<fmt>` contains `%b`. Rule for the guard: a
   match preceded on its line by `||` or `&&` counts as guarded and is not
   flagged. `%s` formats are not flagged.

## Tests

A bats suite `tests/bash32-lint.bats`, run by `just precommit` (`bats` is on
this box; the recipe fails with a message naming it when absent, as for
`rumdl`). Pattern tests only — 3.2 behaviour is not observable here (brief).
Per pattern: each positive case from the brief and the sandbox-lies pre-fix
forms, and each "not flagged" form above. Hook-level: a fixture batch with a
3.2 finding and shellcheck clean yields one JSON object whose
`additionalContext` holds the finding; with shellcheck shadowed off `PATH`,
the notice JSON and the findings both arrive in that one object. Every
assertion checks content, not just status (bats-gotchas vacuous passes).

The lint lints itself: the hook fires on every edit of the script and the
`.bats` file. Regexes are written so they do not match their own text
(`printf[[:space:]]+-v`, not a literal `printf -v`), and positive fixtures are
generated in `setup` or kept in files the hook does not treat as shell. Dogfood
the same day: run the finished lint over this repo's hook scripts and over the
sandbox-lies pre-fix forms (`git log -S` there, read-only).
